# 0023 Tabs, and windows of one launch

Status: accepted 2026-10-12, revised 2026-10-12 for
the options a new tab carries, and for one window (maintainer).
Revised 2026-10-13 (maintainer): a tab dragged out of its window pops
out into a new window of the same launch, reversing the one-window
ruling.

## Context

A window was one process running one session (decisions 0003, 0016), so
a second agent needed a second window. One window should hold several
sessions as tabs, the way a browser window holds pages, each with its
own CLI, pty and meters.

## Decision

- Per tab: the Session and its pty, the agent adapter with its hook
  server, tail and statusline relay, its generated files in
  `<runtime dir>/tab-<id>/` (decision 0016), the bus, the terminal and
  its scrollback, the label, and the window it is in. Per window: the
  active tab, the identity strip, the tab strip, the menu button and its
  drop-down. Per launch: the skin and its last-skin record (decision
  0022), the settings, the mute, the visualization window with a pane
  for every tab of every window, and Housekeeping. `app/tabs.js` keeps
  the order, each window's active tab and the app's end.
- Pop out: a tab dragged along the strip moves, and one released
  outside the window leaves for a new window at the drop point, of the
  source window's size. A live pty cannot leave its process (node-pty
  exports spawn alone), so the new window belongs to the same launch.
  The tab keeps its CLI and pid, its meters and its viz pane. Its
  terminal's buffer, scrollback included, is serialized by the old
  window (`@xterm/addon-serialize`) and written into the new one, and
  the bytes that arrive meanwhile wait in the main process. A window
  whose last tab leaves or ends closes. A window of one tab drags
  nothing out.
- Every call from a window acts on that window: its New tab, its
  chooser, its Close tab and its keys. A skin picked in any window's
  menu reskins every window of the launch, as a browser's theme does
  (a choice taken without the maintainer), so the last-skin record stays
  keyed by the launch's pid.
- Every tab runs in the background: its CLI, adapter and meters. The
  page holds one xterm.js terminal per tab. Only the active one is
  visible. The others stay laid out, hidden, so each keeps its size and
  its scrollback whole. Typing reaches only the active tab.
- The identity strip, the window title, the skin's widgets and the
  visualization follow the active tab. The visualization drops the
  events a tab produced before it became active.
- New tab runs the window's command in the live folder of the active
  tab's CLI (`/proc/<pid>/cwd`, else the folder it started in), with the
  window's environment and the options its provider carries (maintainer).
  Each provider of decision 0021 lists, with their arity, the options of
  its CLI that set up any session the same way, read from the CLI's
  `--help`: `app/metrics/claude/carry.js` (Claude Code 2.1.296, such as
  `--model`, `--permission-mode`, `--settings`, `--disallowedTools`,
  `--tools`, `--add-dir`, `--mcp-config`) and
  `app/metrics/codex/carry.js` (Codex CLI 0.162.1, such as `-m`, `-c`,
  `-p`, `-s`, `-a`). Everything else is dropped: the options of one
  session or one run (`--resume`, `--continue`, `--fork-session`,
  `--session-id`, `--print`, `--worktree`, Codex's `resume`, `fork` and
  `exec`), operands such as a prompt, and any option a list lacks. A
  plain command carries nothing. The new tab's strip names what it
  dropped, `not carried: ...`.
- Labels stay derived (decision 0004). Tabs with one label add their
  folder's name.
- The tab strip is app DOM between the identity strip and the stage,
  24 px high, out of reach of skin CSS (decision 0005). It shows from the
  second tab on, so a window of one tab looks as before. A press picks a
  tab, a drag moves it, a middle click or its close button closes it,
  `+` opens the New tab... dialog (decision 0025). A background tab marks
  output not yet seen, and every tab with a session draws its
  visualization, which shows whether its agent works or is done
  (decision 0015, 2026-10-15). That replaced the mark of work in
  progress.
- The skin area loses the strip's height while it shows. The window's
  minimum height grows by the same 24 px, and a smaller window grows to
  it, so the skin area is never smaller than the validator checked at
  the minimum window size (decisions 0006, 0022). The validator is
  unchanged.
- The File menu gains New tab, Close tab, Next tab and Previous tab, each
  with its shortcut. The shortcuts take no key from the CLI, after GNOME
  Terminal: Ctrl+Shift+T, Ctrl+Shift+W, Ctrl+Tab and Ctrl+Shift+Tab. In
  xterm.js 6.0.0 Ctrl+Shift+letter sends no bytes, and Ctrl+Tab and
  Ctrl+Shift+Tab send only what Tab and Shift+Tab still send. Ctrl+T and
  Ctrl+W stay the CLI's control characters. An open menu takes every
  key first (decision 0022).
- Exit status (maintainer): the app exits when its last tab ends, in any
  window, with that tab's status, or with the last CLI tab's when the last is a monitor tab
  (decision 0027). A window of one tab keeps decision 0003 unchanged. An
  app error decides 125 first and hangs up every tab, and 125 stands
  over the status of the tab that ends last.
- A tab whose CLI exits (maintainer): the tab closes, and the active tab
  passes to its right neighbour, else its left. When it was the only
  tab, the app ends. A status other than 0 of a CLI that exited on its
  own goes under Housekeeping with the dot on the menu button. A tab the
  user closed reports nothing.
- Closing a window with several live tabs (maintainer): a native dialog asks
  `Close N tabs?`, N that window's tabs. A window of one tab closes at
  once, as before. The other windows run on. A
  signal to the app (SIGINT, SIGTERM, SIGHUP) asks nothing and hangs up
  every tab.
- Closing a tab hangs up its CLI alone, by the kill policy of decision
  0016.
- The live checks' probe reports the active tab's child, report and bus,
  as before, and every tab. The page has its own probe for each tab's
  terminal buffer and the meters the skin was last given.

## Why

Per-tab Sessions and adapters reuse the one-session machinery whole:
nothing of decisions 0009 to 0021 learns about tabs. A window of one tab
behaves and looks exactly as before, so every existing check and every
exit status stands. Growing the minimum by the strip keeps the
validator's guarantees without refusing any existing skin.

## Rejected

- The first tab's status as the app's (maintainer): a user who closes the
  first tab by hand and works on in a second would get the hangup's 129.
- A tab that stays open showing its status (maintainer): a window of one tab
  would need a special case to exit as before.
- A tab strip always shown (maintainer): every window would give up its
  height.
- Ctrl+T, Ctrl+W, Ctrl+PageUp and Ctrl+PageDown: the CLI receives them
  today (Ctrl+W deletes a word in readline).
- An "ended" mark on a tab: under the closing rule above, an ended tab
  is gone.
- A validator that checks the skin with the tab strip shown: it would
  refuse skins that are valid in a window of one tab.
- Several windows, a tab moved between them (maintainer): the
  sessions of a launch were tabs of its one window. Reversed for
  a tab dragged out. Dropping a tab on another window's strip, and a tab
  moving to another launch, are still not done.
- A skin per window: a second skin current in one process, a last-skin
  record per window, and a skin pick that would leave the other windows
  as they were. Not asked: the pop-out asks only that the new window
  open in the source window's skin.
- Replaying the pty's raw bytes into the new window: a resize since the
  tab started would reflow them differently from what the user saw.
- One terminal whose buffer is swapped per tab: xterm.js keeps no
  buffer outside a terminal, so a switch would replay the scrollback.
- New tab with none of the window's arguments (the agent's first
  pick): a window started with `--disallowedTools` or a stricter
  `--permission-mode` opened tabs without them.
- A list of the options of one session, carrying the rest (maintainer): an
  option of one session the CLI adds later would be carried, giving one
  session two writers or sending a prompt twice. With the list of
  carried options, an option the CLI adds later is dropped and named in
  the strip until the list learns it.
